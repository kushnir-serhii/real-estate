# 016 — UML diagrams: Supabase, Plektan and where the mock data is

**Status:** in-progress · **Depends on:** 015 · **Route(s):** — (docs only: `docs/diagrams.md`, `docs/diagrams.html`)

## Goal
A developer who opens the repo (or takes the template for a real agency) can see in a few diagrams how the project is built around **Supabase** and **Plektan**, which parts run on **mock data** today and which are the real path that is wired but not connected, and can hover any block to read a short description of what it is. It matters because the code now has two parallel worlds (the `supabase` driver + live service clients, and the `demo` driver + fixtures), and nothing shows the seam between them in one place.

Background: [diagrams.md](../diagrams.md) already exists, but it describes the code as of spec 008. It still says «Sofiacity», has no demo driver, no fixtures, no AI tables, no blog, and nothing in it marks mock data or explains a block. It isn't linked from [README.md](../README.md). This spec replaces its content.

## Scope
- In:
  - **One source:** `docs/diagrams.md`, diagrams in [Mermaid](https://mermaid.js.org/) (GitHub and the VS Code preview render it). Rewritten to the code as of spec 015.
  - **Mock-data marking, the same in every diagram.** Each block carries one of three markers, shown by a text tag (never by colour alone) and explained in a legend at the top:
    - `real`: the production path: Supabase Postgres + RLS, Supabase Auth, R2, the live Plektan / Telegram / LLM / Turnstile / geocoder calls. Wired, **not connected to any account yet**.
    - `mock`: exists only for demo or fixture mode: the in-memory store, the typed seed, the demo session cookie, in-memory photo uploads, service fixtures, the agency consts, the generated `supabase/seed.sql`.
    - `seam`: code that serves both and picks one by env: the `src/lib/db/*` facades, each service client's entry, `admin-session.ts`, `photo-url.ts`.
  - **A «Blocks» table under every diagram** (`Block | Data | What it is | Code`): one row per block. «What it is» is **one short sentence, at most 140 characters**: it is the tooltip text and also the fallback where hover doesn't work (GitHub, print, screen readers). «Code» holds the path in the repo and the env variable that switches the block, when there is one; it is not part of the tooltip.
  - **A plain tooltip on every block of every diagram** in a generated, self-contained viewer `docs/diagrams.html` (opens by double-click, no network): hover or keyboard focus on a block shows a small ordinary tooltip with the block's marker and its short description, nothing more (no cards, links or panels). Generated by `pnpm diagrams` from `docs/diagrams.md`; a test fails when the two drift (same pattern as `pnpm seed:sql`).
  - **The diagram set** (12 diagrams, see Slices):
    - structure: system context · mock-data map · data-driver seam · domain model (all 12 tables) · Plektan API ↔ our model;
    - behaviour: public read on each driver · Plektan sync · lead delivery (form and AI) · lead retry cron · properties source switch · AI assistant turn · admin sign-in and photo upload on each driver.
  - Docs wiring: links from `docs/README.md` and `CLAUDE.md`; a rule in `docs/conventions.md` that a slice which changes a table, a driver, a service client or one of these flows updates the diagram and its «Blocks» row.
- Out:
  - Any change to app code, schema, migrations, seed or behaviour. If a diagram shows the code is wrong, it goes to **Open questions**, not into a fix.
  - Diagrams of the UI (components, pages, design tokens) and of the blog editor. The blog tables appear in the domain model only. The old «Application layers» class diagram is dropped.
  - A route inside the app that shows the diagrams; hosting them anywhere.
  - Connecting any account. The `real` path is drawn from the code and marked as not verified live (decided in [011](011-demo-template.md)).
  - Translating the diagrams to Ukrainian (docs stay in English).

- **Open (2026-11-12), found while drawing the flows (nothing fixed, the diagrams show what the code does):**
  - the demo seed sets `settings.properties_source` to `admin` (`src/lib/demo/seed/index.ts`), while the migration default is `plektan`; the demo store holds `plektan`-sourced listings in `admin` mode. Intended?

  - `pnpm sync` on the `supabase` driver with an empty `PLEKTAN_API_KEY` would write the Plektan fixtures into that database; only the GitHub workflow's key check guards against it;
  - a lead whose Telegram channel runs out of attempts raises no alert (only exhausted Plektan delivery alerts the manager);
  - `getDistricts` is exported from the Plektan client and has a fixture, but nothing calls it.
