# 022 — Stack move: Railway + Payload CMS + Postgres, Cloudflare in front

**Status:** draft · **Depends on:** 021 · **Route(s):** `/admin` (Payload), all public routes unchanged

> **On hold.** Not built until the client approves the stack change. Until then the current stack (Cloudflare Workers via OpenNext + Supabase + R2, own admin) stays the target.

## Goal
The site runs as one Node service (Next.js + Payload CMS) on Railway with Postgres on Railway, and Cloudflare stays in front for photos (R2), WAF, DDoS protection and admin access. Admins get a ready-made CMS (users, roles, drafts, media, blog, SEO pages) instead of our own admin, so each agency built from the template costs less code to maintain. Visitors see the same site.

Why (stack review, 2026-11-16):
- A ready CMS replaces the custom admin, auth and roles we would otherwise maintain per client; the blog and future content types become collections.
- A plain Node server removes the Workers limits (bundle size, CPU time, no `sharp`) and the OpenNext layer; long Plektan syncs and Payload run as is.
- Rough monthly cost for a typical agency (≈50k visits, ≈2k properties, ≈20 GB photos): Railway app ~$7–12 + Railway Postgres ~$3–6 + R2 ~$0.15 + Cloudflare free ≈ **$10–18**, against ≈ $30 now (Workers $5 + Supabase Pro $25). Check current prices before quoting the client.

## Stages
1. **Development (free tiers only):** Vercel Hobby (app) + Neon Free (Postgres, a branch per preview deploy) + Cloudflare Free (R2, Turnstile, Image Transformations). Cloudflare DNS stays *DNS only* in front of Vercel (Vercel doesn't support a proxy in front); WAF and Access come with stage 2.
   - Vercel Hobby is for non-commercial use: fine for development and demos to the client, not for the client's live site.
   - Hobby cron runs at most once a day: the Plektan sync and lead retries are triggered by an external scheduler (GitHub Actions or a Cloudflare Worker cron) calling `/api/cron/*` with a secret.
   - Neon Free: compute sleeps when idle and has a monthly compute-hour cap; acceptable for development.
2. **Production:** switch to Railway (app + Postgres) with Cloudflare proxied in front. The switch is configuration only: env vars, DNS, cron moved to a Railway cron service.

**Portability rule (both stages):** the code stays host-agnostic: Node runtime only, no `@vercel/*` packages, no Vercel Blob / KV / Edge Config, no `vercel.json` crons the app depends on; storage is R2 through the S3 API, the database is any Postgres behind `DATABASE_URL`, images go through the Cloudflare loader (not Vercel image optimization).

## Scope
- In:
  - Payload 3 (≥ 3.73, needs Next ≥ 16.2) inside the Next app. **Postgres is the one real database** everywhere: production, previews and local development (a Neon branch). SQLite only for the offline demo, so a fresh clone still runs with no Docker, keys or network.
    - Why: SQLite and Postgres need two separate Drizzle migration sets and behave differently in SQL (JSON, case sensitivity in `like`, types). Only Postgres migrations are generated and committed; the SQLite demo uses Payload's schema push, no migrations.
    - Driver contract tests run on Postgres in CI (a Postgres service container in GitHub Actions or a throwaway Neon branch); the SQLite demo gets a smoke test only.
  - Collections mirroring today's data: properties, media (photos, S3 adapter → R2), agents, leads, pages + SEO, settings, posts (blog), admin users with roles.
  - The `src/lib/db/` facades reimplemented on the Payload Local API; public pages and components don't change.
  - Leads pipeline (store first → Plektan `addAdvert` → Telegram, retries) and Plektan sync writing through the Local API; the «one source of truth» setting kept.
  - Hosting in two stages (see «Stages»): Vercel + Neon on free tiers during development, then Railway for production; cron endpoints `/api/cron/*` protected by a secret and called by an external scheduler.
  - Cloudflare in front of Railway: proxied DNS, WAF + rate-limit rules on `/api/*` and forms, Cloudflare Access on `/admin`, cache rules for `/_next/static/*` and photos only (HTML stays in Next's cache), image resizing via Cloudflare Image Transformations or sizes made on upload (not `next/image` on the server).
  - Removing the Supabase driver, Supabase Auth, the own admin and OpenNext/wrangler once Payload covers them.
  - Docs: `CLAUDE.md`, `docs/product.md`, `docs/setup.md`, `docs/conventions.md`, `docs/diagrams.md`.
- Out:
  - **Database backups (not in the MVP, see «Known risks»).**
  - Caching HTML in Cloudflare with purge from Payload hooks (later, only if traffic needs it).
  - Visitor accounts (019/020): re-planned on Payload auth in a separate pass, see «Open questions».
  - Any change to the public design or routes.

## Data
- Payload collections and migrations (Drizzle, generated by Payload) replace `supabase/migrations/` and RLS; access control moves to Payload `access` functions (public: published properties and posts only; leads: admins only). The database is reachable only over Railway's private network.
- Seed: the typed demo seed in `src/lib/demo/seed/` loads into Payload (SQLite locally, Postgres on a fresh deploy); `supabase/seed.sql` and `pnpm seed:sql` go away.
- Photos: Payload media → R2 through `@payloadcms/storage-s3`; existing R2 keys are kept where possible.
- External clients (`src/lib/plektan`, `telegram`, `llm`, `geocode`, `turnstile`) keep their fixture modes unchanged.

### [ ] 7. Cloudflare in front, origin locked + docs
- **Build:**
  - Image loader for Cloudflare Image Transformations (or sizes on upload).
  - **Origin lock (Cloudflare can't be bypassed):** Railway accepts requests on its generated `*.up.railway.app` domain and for the client's host sent straight to Railway, past Cloudflare, so WAF, rate limits and Access alone guarantee nothing. Therefore:
    - remove the generated Railway domain; keep only the custom domain;
    - a Cloudflare Transform Rule adds a secret request header (`X-Origin-Auth: <ORIGIN_SECRET>`) to every proxied request;
    - Next middleware rejects (403) any request without the right header; exceptions: the health check path (returns only `ok`) and cron calls over Railway's private network carrying `CRON_SECRET`;
    - for `/admin` and `/api/admin/*` the middleware also verifies the `Cf-Access-Jwt-Assertion` JWT (signature against the team's Access certs, `aud` = the Access app), on top of Payload's own login.
  - Setup steps in `docs/setup.md`: proxied DNS, **SSL/TLS mode Full — not Full (Strict)** (Railway docs: Strict breaks during Railway's certificate renewals), Transform Rule, WAF and rate limits on `/api/*` and forms, Access application on `/admin`, cache rules (static + photos only), how to rotate `ORIGIN_SECRET`.
  - Update `CLAUDE.md`, `product.md`, `conventions.md`, `diagrams.md`.
- **Agent:** backend · **Model:** sonnet (docs: haiku)
- **Accept:**
  - [ ] a request to the origin without the secret header gets 403; with it, the site works.

## Known risks
- **No database backups in the MVP** (decision 2026-11-16). Railway's built-in database and volume backups (scheduled snapshots, point-in-time recovery) are **Pro-only** ($20/month minimum); on Hobby the backup limit is zero (Railway staff answers on station.railway.com, checked 2026-11-16 — recheck before relying on it). So on Hobby the only mitigation is that every lead is also sent to Telegram (and Plektan when on) and can be restored by hand.
  - **Add backups when any of these happens:** the first real client goes live, a few hundred leads are stored, or data appears that can't be rebuilt from Plektan.
  - **Options when backups are added:** Railway Pro (built-in snapshots + point-in-time recovery, from $20/month) or stay on Hobby with the scheme below (~$0 extra).
  - **Planned backup scheme (Hobby):** twice a day `pg_dump` from Railway → dated file in R2 (keep 14–30 days) → `pg_restore --clean` into a free Neon project as a warm standby and a proof that the dump restores. Failover = point `DATABASE_URL` at Neon. `pg_dump` and Neon must match the Railway Postgres major version.
- Payload versions are tied to Next versions: upgrades go together.
- Railway Postgres is one container with one disk, no point-in-time recovery; a single region (EU West).
